# Callback-thread relay experiment

This fixture tests a possible solution to Rust worker-thread callbacks aborting the Dart VM. We have reproduced the crash locally; we have not found a downstream report of this failure. It is based on upstream `main`, uses UniFFI 0.31.2 and Rust 1.85, and is not enabled in the generator.

`call_bytes_thread` is the failing call shape: a generated Dart function enters Rust, Rust spawns another worker, and that worker calls a Dart `Sink` before Rust joins it. The relay runs the original exported UniFFI function on a worker and services queued callback requests on the original Dart thread. It calls the actual generated Dart vtable functions, including method conversion, error handling, clone and free.

The native code uses the vtable type and exported functions generated by UniFFI's macros. It does not substitute a Rust implementation of the Dart callback. Callback requests return owned Rust values through channels; stack output pointers are not retained by queued callbacks. Queue and handle-route locks are released before calling Dart.

## Run locally

From the repository root, with Python 3, Dart and Rust installed on a 64-bit desktop host:

```sh
rustup toolchain install 1.85.1
python3 fixtures/callback-thread-relay/probe/run.py --dart /path/to/dart
```

The default Rust toolchain is 1.85.1; `--toolchain` overrides it. The runner downloads dependencies normally; use `--offline` to use cached Cargo and Dart packages only. Dart 3.13.0 was used for the verified run. A Rust linker/toolchain appropriate to the host is required. Windows users can invoke the same script with `python` or `py -3`.

The runner selects `.so`, `.dylib` or `.dll` and handles subprocess timeouts for Linux, macOS and Windows respectively. Only Linux x64 has been verified so far. Other 64-bit desktop results are requested, not claimed. This is not a device runner for Android/iOS; those need a Flutter/native build harness. 32-bit hosts are rejected because their handle ABI needs separate work.

Set `PUB_CACHE` if your normal package cache is not writable, and `CARGO_TARGET_DIR` to choose an isolated build directory. The default is `target/relay-validation`. Runtime cases have a 120-second watchdog; `--timeout` adjusts it for slower machines. A timeout always fails the case, including the expected-crash control.

Results and child-process logs are written under `target/relay-results/` in this checkout, including partial results when a subprocess fails or times out. The JSON records OS, architecture, Dart/Rust versions, source revision, case durations and outcomes. No `upstream` remote is required. The normal repository CI does not execute this standalone probe; a green check is not a probe result. The script builds the fixture and this checkout's generator, regenerates Dart bindings, and constructs three isolated packages:

- Baseline: original generated native symbols. The same-thread control must pass, and the worker-thread control must terminate with the specific Dart wrong-thread callback diagnostic. A timeout or compile failure does not qualify.
- Relay: only six `@Native` symbol annotations select fixture relay entry points. Generated callbacks, converters and clone/free implementations are retained. Test-only getters expose the Dart registry size.
- State mutation: the same relay and expected return value, but the Dart callback's state update is removed. The test must reject it, demonstrating that a plausible return value alone cannot pass.

Relay cases cover the direct call path, the Rust worker/join reproducer, 80 calls from eight concurrent Rust workers, explicit foreign-handle cloning/freeing on a worker, a declared callback error roundtrip, nested Dart-to-Rust-to-Dart calls, and 100 repeated calls. Each checks that Dart callback handles and native routes are empty after the operation. Assertions use explicit exceptions, not optionally disabled Dart `assert` statements. Each runtime case has a process watchdog; core dumps are disabled for the abort control.

## Limits

This is a fixture-specific experiment, not a general binding-generator fix. It supports one Dart isolate and callbacks bounded by an active synchronous call. The vtable is registered once per process. It does not support callbacks that outlive the call, cross-isolate registration, async Dart callbacks requiring event-loop progress, cancellation or shutdown with outstanding callbacks. Missing callback routes currently fail loudly; they are not a production error policy.

Moving the native operation onto a worker changes its thread. Thread-affine native libraries need a separate design. Runtime behavior on Windows, macOS, mobile, 32-bit targets and Dart AOT has not been verified. The tests check callback-handle cleanup, not general native heap leak freedom; existing buffer-ownership behavior on main is unchanged.

No experimental Dart APIs or shared-data VM flags are used. No other PR branch is part of this fixture's base.

## Reporting a run

Attach `target/relay-results/results.json` and any failing case's `.log` to the draft PR. Include the device/CPU and whether the generated-Dart state and handle cleanup checks passed. The baseline worker abort and the deliberately broken callback are expected negative controls; the runner should mark both `passed: true` only when they fail in the intended way. Do not report either alone as a new relay failure.
